# Service child bootstrap: authority boundary before source integration

Status: source audit and exact proposed delta, **not an installable adapter**. No service was installed, started, stopped, or exposed. No producer registry is changed. `source-records.json` records the precise inspected bytes; pinned files retain their upstream ownership/license under the adjacent `../LICENSE.upstream`. Candidate and native-working-source records are explicitly distinguished from pristine upstream source.

## Existing channels and the safe descriptor allocation

The profile-4 launcher candidate `../fixtures/003-launcher-payload-layout.after.ts:624-627` starts the complete payload entry with `serve`, original service context in the environment, and `stdio: ["inherit", "inherit", "inherit", "ipc"]`. Descriptor **3 is Node IPC**. `apps/server/src/cloud/serviceLauncherClient.ts` accepts launcher context only when `process.connected` and `process.send` establish real IPC, verifies protocol and child version, and exchanges original update/prepared/committed messages. Replacing FD3 with a bootstrap pipe breaks this protocol.

The concrete eventual spawn delta is descriptor 0 only: args become `serve --bootstrap-fd 0` plus explicitly reviewed effective mode/host settings, and stdio becomes `["pipe", "inherit", "inherit", "ipc"]`. An authorized native issuer supplies one original `DesktopBackendBootstrap` JSON line through the captured child's stdin, then closes stdin. Keep descriptor 3, original context, child-object fencing, listeners, trial timers, rollback, exit-78 behavior, and signal cleanup unchanged. Do not serialize a secret into argv, service.env, runtime state, or a renderer call. A failed authorized write must kill/reap only that captured child and enter the original failure transition; never replay an uncertain write to another child.

This is a precise delta specification, not an executable patch: there is currently no trustworthy issuer available to this Node-only launcher. Adding an interface whose caller merely returns `authorized: true` would not implement that missing authority.

## Why the existing direct bootstrap cannot simply be copied

* `src-tauri/src/managed_host.rs` stores private configuration containing artifact path/digest, environment identity, bootstrap secret and optional live browser capability. Its bounded exclusive `launcher.lock` lease fences selection/start. The native filesystem gate rejects ownership-disabled volumes; a Node UID/mode check is not equivalent. At the audited snapshot the configuration had no service-owner selection mode. The subsequent [ownership restriction](OWNERSHIP-ENFORCEMENT.md) now defaults legacy configuration to Direct and blocks direct startup/probe for Service mode. A native migration/issuer must still be implemented before selecting Service; the restriction alone does not authorize service attachment.
* Direct Root spawn explicitly passes `--mode web`, loopback host, original bootstrap JSON on FD0, and Tailscale disabled. The envelope's `mode: desktop` does not override the CLI flag. Original `cli/config.ts` applies flags, environment, then bootstrap precedence. Merely sending the same envelope from serviceLauncher instead changes effective mode unless flags are also chosen explicitly.
* Original `cli/server.ts` enables `launcherWatch.ts` only for desktop mode plus a bootstrap token. That watcher captures `process.ppid` at module load, detects parent change every two seconds and interrupts the backend; it is separate from Node IPC. Systemd already has KillMode=mixed and launchd process-group cleanup. Whether service children use web or desktop auth/lifecycle policy requires an explicit reviewed decision, not an incidental bootstrap side effect.
* `bootstrap.ts` has a one-second optional read. Missing descriptor/EOF/timeout can mean no envelope and fallback configuration. A mandatory private profile cannot depend on this fallback. A required-bootstrap gate scoped to real service context would need a separately reviewed source change, after the issuer exists.
* `readServiceEnvironment` permits inherited/service.env settings such as host, mode and bootstrap FD. Explicit `--bootstrap-fd 0` is essential to avoid accidentally reading IPC FD3. The native issuer must also define authority over effective exposure/settings and conflicting environment values. Original `ExposureRuntime.ts` can compute settings/policy but does not implement a secret reader or a long-lived native owner.

## Required native transaction, before enabling this delta

1. Supply a durable native-private issuer available when the GUI is absent. Bind it to native-selected, fully verified profile-4 manifest, environment identity, private owner directory and ownership-aware filesystem gate. No arbitrary serialized receipt, renderer path, boolean authorization acknowledgment or new ad hoc crypto.
2. Under the existing bounded owner lease, distinguish direct-owner from service-owner configuration. Reconcile a currently captured direct child without trusting persisted PID records; never delete SQLite ownership locks. Atomically rebind the exact selected artifact digest and service ownership mode before permitting a service spawn. Root's stopped-service behavior must not launch a competing direct owner.
3. Read protected configuration and original settings/policy through that authority, create a fresh original twelve-hour-window bootstrap HMAC, sanitize conflicting inputs, and issue the original envelope only to the actual captured service child. Hold the necessary ownership fence through an unambiguous outcome. Define interrupted/uncertain issuance without replay.
4. Preserve original update handshake ordering. `serverRuntimeStartup.ts:640` waits for `launcher.prepareTrial` before `options.activate` at line662. Do not make the launcher's prepared/committed acknowledgment depend on an HTTP-ready/activated state: that can deadlock a trial. Ownership preparation and runtime activation must remain separate milestones.
5. Treat browser socket path/key/generation as a live Root-owned capability. A background service must not retain a stale GUI socket authority forever; reconnection/revocation requires the existing independently authenticated attachment semantics.

## Exact trust and release gaps

The current proof-9 endpoint binds nonce, environment, origin, server version `0.1.7`, and orchestration protocol; it does not bind the selected payload manifest or distinguish same-version C21 from profile4. Native service selection must therefore retain the exact expected digest independently. The five profile4 source records and original version are necessary but do not create a released profile4 artifact. No genuine selected profile4 payload, native-private Effect publisher binding, service-ownership configuration migration, or durable bootstrap issuer currently exists. Current C21 is deliberately rejected by the service installer. Do not mutate a C21 payload in place or invent a version/feed to bypass this gate.

Next coherent implementation scope is the native service-selection/issuer contract and direct-owner migration, followed by the descriptor-0 delta and a mandatory-bootstrap regression fixture. Tests must cover a real IPC prepared/committed exchange, service.env FD3 collision, no issuer/timeout/malformed envelope, stale generation/config replacement, concurrent Root start, captured-child-only cleanup, GUI disconnect, and unchanged update rollback. Until those dependencies are implemented, producing a runnable child-reader patch would conceal a product-critical ownership and authentication gap.
