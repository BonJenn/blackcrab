# Full native UI activation and host integration

This subtree prepares the complete verified pinned UI as an owned source library. The owned active root at `apps/mobile/App.tsx` invokes this entry once per process and keeps the full App mounted while a native full-screen Legacy hosts destination is shown. It never installs dependencies. The generator first calls the existing complete-consumer verifier, then copies the entire authenticated consumer payload and applies only 20 exact before/after SHA-256 adapters. Every modified original is retained under provenance. No upstream configuration, EAS command, package script, or App module is executed. The generated upstream app.config location is an owned fail-closed guard; upstream EAS bytes are retained only as inert provenance.

Run with the existing Node26 toolchain:

```
node --test mobile-experience/activation/activation.test.mjs
node mobile-experience/activation/cli.mjs generate VERIFIED_CONSUMER ABSENT_OUTPUT
node mobile-experience/activation/cli.mjs verify VERIFIED_CONSUMER GENERATED_OUTPUT
```

The output must not exist. The generator never changes the consumer, active App, vendor, shared packages, native configuration, dependencies or installed packages. Publication fails on an existing path; failed publication removes only the newly created owned output. Verification recomputes the authenticated consumer + adapter byte plan and rejects missing/extra files, symlinks, hardlinked files, modified templates, input drift, or changed manifests. The registry also pins the generator and owned helpers. Output metadata is deterministic: no timestamps, credentials, absolute source paths or machine IDs.

## Process ownership handoff for the root integrator

The original App has12 module-installed disposer services, plus splash prevention and workspace-selection hydration. Its foundation ManagedRuntime, connection AtomRuntime, global AtomRegistry and derived Atom runtimes share process-lifetime services. A screen mount is not a service lifetime boundary; unmounting cannot dispose this graph safely. The generated `OwnedActivation.ts` therefore exports a one-time boot activation function, not a default App to conditionally import or mount.

On a fresh process, remove `createNativeManagedEnvironmentsClient` imports, state, start/stop effect, and Workspaces tab from the separate legacy App. No old managed reader may ever start. The root supplies an explicit ownership assertion to `activateFullNativeUI`, then mounts the returned full App once and keeps it mounted for the entire process. Legacy Hosts/queues can be shown as a separate view/overlay without unmounting the full App or creating a second managed foundation. Their identifiers, credentials, durable queues and protocol remain unchanged. No translation into the managed catalog is performed.

Concurrent activation calls share one promise; import success and failure are sticky. A partial import may already have installed services, so neither failure nor closing a legacy view retries or restarts the full foundation. Foundation or adapter changes require a fresh process. Root integration must not use a tab's useEffect to import/dispose/reinitialize the original App. The normal pinned background/wakeup/notification and Fast Refresh hooks are retained, but this preparation does not certify hot foundation replacement under the new process guard.

The owned root removes the previous managed reader from `LegacyApp`, uses a sticky process guard against either prior or later legacy reader construction, and reveals managed navigation for links, notifications, shortcuts and incoming shares. While Legacy is visible, managed on-screen notification suppression is cleared and its voice overlay is hidden. Active dictation blocks entry into Legacy; a raced recording start reveals managed view. Both transitions dismiss the keyboard. Native platform/device acceptance remains a separate gate. The generated tree reports `sourceIntegrated:true`, `nativeValidationPending:true`, and `readyForMount:false`. These are provenance/certification fields, not a runtime feature flag; only native boot/catalog/control acceptance can certify readiness. Its own identity policy is Blackcrab Remote, scheme `blackcrab-remote`, bundle `dev.blackcrab.remote`; use the reviewed own platform config, never the copied inert T3/EAS configuration.

## Storage and feature boundaries

The original SDK `Schema.fromJsonString(ConnectionCatalogDocument)` decodes/encodes `blackcrab.mobile.managedCatalog.v1`. Existing bearer sessions are retained as sessions, with no pairing/bootstrap reinterpretation. Only null means an empty catalog. Blank, malformed or unsupported data remains untouched and returns a generic error without native/parse causes or credential content. All updates/read visibility are serialized behind durable whole-value writes; failed writes and mutating/throwing transforms cannot publish an uncommitted catalog. There is no upstream legacy migration, delete, clearing or log-on-corruption path.

The generated native SecureStore adapter passes that existing managed key through unchanged, prefixes every other key with `blackcrab.mobile.native.v1.`, and writes with `WHEN_UNLOCKED_THIS_DEVICE_ONLY`. The full UI database uses `blackcrab-native-client.db`; old Hosts/queues storage is never opened by these adapters. The code keeps the complete pinned connection/foundation and feature tree, including agent messages, outboxes, permissions, uploads, settings, notifications, shortcuts, workspaces and previews. Only identity/storage integration, upstream cloud public configuration, upstream account-provider activation/deactivation, automatic OTA checks and internal showcase capture are adapted. Own cloud/updates require separate reviewed implementations; no upstream cloud or update configuration is activated by inherited flags/extras.
