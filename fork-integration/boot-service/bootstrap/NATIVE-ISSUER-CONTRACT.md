# Same-binary headless bootstrap issuer contract

Proposed implementation boundary; no CLI dispatch, service unit, helper process, or issuer is activated by these documents. This design resolves the issuer's location: a headless subcommand of the **same compiled native Root executable**, dispatched before Tauri/legacy startup. It does not require the GUI to remain running. The selected native executable and the selected service payload remain separate trust anchors.

## Executable and ownership selection

A native-only service installation transaction must publish a private binding outside the immutable payload. It binds the canonical installed native executable (regular file, reviewed identity/digest and executable code-signing requirement where available), exact compiled profile4 manifest digest, owner-root identity, environment ID, and service generation. The OS unit's program/arguments are generated from that native transaction. No PATH lookup, environment-provided helper path, renderer path, or service.env override selects the issuer. Moving/replacing the native executable requires a native republish operation. Hashing an arbitrary path supplied by the launcher does not authorize it.

The launcher may pass a bounded fixed selector/generation as a lookup key; that value is not authority. The helper derives the actual root and selected manifest from its installed private binding and its compiled trust anchors, validates ownership-enabled filesystem/private ancestor/no-link rules, and requires Service configuration. It must reject C21, Direct, stale generation, mismatching environment, changed selected digest, unreviewed profile4 records, or an unknown update target. Current compiled pins authorize only one exact original version: later updates need a separately authenticated native selection publication before a new target can be bootstrapped. Original service state is not an arbitrary digest authorization list.

A same-user process can execute the native binary and inspect its own user's memory/files; this mechanism is not a sandbox against malicious code running as that UID. The enforceable boundary is other users, renderer/untrusted remote arguments, accidental path/env substitution, stale ownership and competing compliant launchers. Private anonymous pipes provide local process topology, not independent cryptographic identity of an arbitrary caller. If adversarial same-UID isolation is required, a signed privileged service/audit-token IPC design is an additional product requirement.

## Leases and lifecycle

Use the existing `launcher.lock` for bounded **configuration/start transactions**, not the entire service lifetime. Holding that lock forever would make existing Root status/start wait 120 seconds and fail; holding it until trial HTTP readiness can deadlock original prepare/commit activation. A separate native private `service-owner.lock` lease provides helper lifetime exclusivity, acquired before `launcher.lock`, with one fixed lock order everywhere. Root's Service marker forbids a direct spawn even while neither lease is held. The migration transaction must establish that restriction under launcher.lock before installing/enabling the OS unit; no migration is included here.

The helper starts first, acquires service-owner.lock, then launcher.lock, verifies binding/config/artifact, computes the original bootstrap token/envelope, and announces a bounded prepared frame. The launcher **does not spawn** until that frame is completely decoded. The helper holds launcher.lock until the launcher's captured child pipe has accepted and closed the complete envelope or until failure. Release this transaction lease after durable issuance is recorded; do not wait for HTTP readiness, original `prepared`, or original `committed`. Keep service-owner.lock while the launcher session lives. A later epoch reacquires launcher.lock and rereads/validates all current native selection/config before issuing new bytes.

A launcher disconnect kills no foreign PID. The helper closes its pipes, releases its captured leases and exits. The original launcher remains responsible for its actual Child cleanup and original OS-unit process-group semantics. Helper EOF/failure while a captured child is running is a fatal launcher condition: gracefully terminate/reap that exact captured child before exiting and allowing the OS manager to restart. Do not leave an unfenced child alongside a new helper. GUI disconnect has no relation to this pipe and does not stop a service child.

## Bounded private framing and sequencing

Transport: the launcher spawns the pinned helper with private stdin/stdout/stderr pipes; stderr contains generic diagnostics only. One helper session per launcher, one issuance outstanding, monotonically increasing epochs and native random session identifier. Frames are newline-delimited JSON with deny-unknown-fields, fixed protocol version, maximum 64 KiB/frame, maximum bounded transcript bytes and explicit phase deadlines. Secrets appear only in the one envelope frame on private stdout; never log frames. The helper must set an appropriate process memory/logging policy. No PID/command/path/digest authority arrives in requests.

1. `begin {protocol, epoch, selectedVersion, role, updateId?}` requests lookup against native selected state. These fields may constrain a request but cannot authorize a different artifact. Helper returns `prepared {protocol, session, epoch, selectedVersion, generation, envelope}` only after native verification and lease acquisition. It computes the unchanged original HMAC from protected config. A response is not an `authorized:true` acknowledgment: the native process has performed actual verification and supplies the actual secret-bearing bootstrap bytes.
2. Launcher validates framing/bounds, retains those bytes in memory, and spawns exactly its already-selected fully verified payload with stdin pipe0 and IPC3 unchanged. Register captured-child error/exit/message listeners before issuance. Then write one envelope line and close stdin immediately; bootstrap reader's one-second timer must never depend on a later native round trip. Apply a reviewed mandatory-bootstrap gate for real service context so EOF/timeout cannot fall back to default configuration.
3. Launcher sends `issued {protocol, session, epoch}` only after its captured stdin completion callback; helper records the epoch outcome and releases launcher.lock. This is delivery bookkeeping, not proof the child authenticated or became ready. On uncertain write/EOF, invalidate the issuance, terminate/reap only that captured child, and never replay the same frame. A new epoch requires revalidation and a fresh envelope.
4. Original child-to-launcher `prepared` and launcher-to-child `committed` continue exclusively over IPC3. At `serverRuntimeStartup.ts:640`, prepareTrial occurs before activate at line662. The issuer must not gate the committed response on a ready endpoint or add a round trip to that exchange. Original rollback/timers/state transitions remain unchanged.
5. Before restarting or starting a trial, the launcher finishes captured-child termination/reap, retires the old epoch, then requests the next one. Original active/trial/rollback version must be explicitly native-selected; unselected newer version is rejected before spawn. A helper failure during handoff is surfaced as original launcher failure, never converted into a default web start.

Holding service-owner.lock across children avoids two compliant launchers concurrently issuing envelopes. A durable private journal records generation and epoch disposition before acknowledgment; uncertain issuance remains nonreplayable after restart. It does not record PID authority or secrets. A native-selected new session may proceed only after original SQLite ownership proves exclusive; never delete the SQLite lock or signal a persisted PID. Exact journal recovery and service-state rollback coordination must be implemented together, not inferred from an `issued` frame.

## Required implementation/test slices

A. Native headless dispatch before Tauri startup, fixed installed binding and private FS gate, real protected Configuration reader, native session/lease/journal module. Tests cover no GUI/legacy startup, wrong binding/role/profile/digest, moved executable, ownership-disabled filesystem, stale generations, lock ordering and bounded waits. The current private ownership enum is a restriction only; a native lease-held migration issuer must be added separately.

B. Original launcher candidate: private helper capture plus descriptor-0 bootstrap, exact listener/IPC3 preservation and original errors/timers. Use real lightweight subprocesses: helper ready before child; actual Node prepared/committed IPC; delayed preflight beyond one second still succeeds because no child exists yet; issued uncertain write, malformed/oversized/repeated frames, helper death/EOF, child exit between spawn and write, stop during preflight, inherited/service.env FD3 override and stale helpers. No envelope or service.env can override fixed native selection.

C. Trial race regressions: prepared before activation commits without issuer readiness deadlock; GUI status cannot stall original handshake; concurrent launcher rejected; original rollback to previous selected version; unknown target rejected while old child remains intact; stale child messages ignored; helper session restart cannot replay old issuance; uncertain journal write fails closed. Preserve original thirty-minute trial timeout and captured-process shutdown semantics, not a new blanket HTTP startup deadline.

D. Only after the genuine native issuer/migration and v2 manifest/profile-bound identity adapter exist: build a real selected profile4 artifact and run isolated OS-unit acceptance. No activation is justified by the current prep code or C21 artifact.
