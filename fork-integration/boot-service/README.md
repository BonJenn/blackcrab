# Owned local boot-service candidate

This directory is preparation, not an installed service or remote-control API. No production registry, Root command, host producer, mobile input, dependency or lockfile is changed by these files. The upstream target is `BonJenn/t3code` commit `7f02de2eb8e253e0ec23f005b3cfff8e2c963be8`, archive SHA256 `eab8b879f121a8f917a654f9eb2d145295152082a700095fbb6c1024c0db83b6`. Exact original/effective source, diff hashes and the upstream MIT license are preserved.

## Candidate behavior

Five reviewed deltas are defined in `registry.json`:

1. `bootService.ts` retains its original launchd/systemd managers, quoting, stop deadlines, restart handoff, persistence and version checks. It uses `blackcrab.service` and `com.blackcrab.desktop.managed.service`. Its installer is an injected native-private local-artifact port; the absent port fails before attempting an upstream download.
2. `pinnedRuntimePaths` uses `runtime/versions/<version>/payload/t3`. The original complete managed artifact lives unchanged in `payload`; the completion sentinel and profile metadata live outside that verified tree.
3. `serviceLauncher.ts` selects the same payload path and requires a private, bounded, no-follow owned layout marker, exact version/protocol, and matching payload-manifest hash. Original captured-child transitions, IPC handling, database trial/rollback, stop marker and ownership-exit78 behavior remain in use. This startup metadata gate does not replace the complete native artifact verifier.
4. The private launcher protocol becomes **4**, because the payload subdirectory is an incompatible runtime layout. State/context protocol3 is refused. Public orchestration protocol2 is unchanged. Original protocol3 message/trial semantics are retained; this is an independent owned profile, not layout compatibility with an older launcher.
5. `selfUpdate.ts` advertises no updater capability, refuses update and desktop-commit operations, and does not invoke automatic runtime pruning until an owned release/publisher/pruner exists. Service ownership alone must not enable an unconfigured upstream downloader. This gate is explicit missing functionality, not completed updater parity.

`local-runtime.mjs` prepares an opaque receipt after checking the real producer verifier, the native-selected exact manifest digest, the five exact profile descriptors, and the existing canonical/private Blackcrab owner root marker. It computes only `ownerRoot/host` paths. The returned plan cannot be used as an authority-bearing JSON object, and planning creates no host/runtime directory. Original3 and C21-style packages are rejected even if their inventories are self-consistent. The generic JavaScript verifier is integrity evidence; production must still obtain its digest/selection from the existing stronger native artifact trust path.

`LocalInstaller.ts` captures version/platform/base-dir/final paths in a native-private binding. Its mandatory transaction stages verified files, runs the original version validation against staging, then commits. Validation failure does not commit; release cleans only the port's own unpublished staging. A publication failure is not an invitation to overwrite or retry uncertain state. The adapter does not read the original HTTP or release-URL ports. The native transaction/cross-process lease/no-overwrite publisher is an integration requirement, not implemented by this preparation module.

## Required production wiring

- Fresh source: promote all five reviewed records together, copy the typed local-installer adapter and a concrete native transaction port, and build a new profile4 host artifact. Do not install the current C21 host or reuse an original3 state document. Bind an exact owned layout marker `{schema:1, profile:"blackcrab-local-service-layout-v1", protocol:4, version, manifestSha256}` outside `payload`. A new service artifact/release version and profile transition must be explicit; a same-version/different-digest runtime must not overwrite an existing installation.
- Native installer: reuse the existing Root-owned paths, marked private directories, bounded cross-process lease and verified payload primitives. Copy/clone the unchanged complete artifact to private staging, run its original `--version` validation, verify again, publish without replacement, and durably publish the completion/profile metadata. No generic verifier exclusions for sentinel files and no hardlink/symlink alias to another mutable package.
- Private bootstrap: original `Launcher.#startChild` currently inherits stdin and reserves FD3 for Node IPC. Add an owned bootstrap reader/adapter before production: read the native-private configuration/settings under the owner lease, retain original policy/exposure semantics, send bootstrap on a newly captured stdin pipe, keep IPC FD3 intact, and exclude controller secrets from argv/environment/renderer/state projections. The current candidate deliberately does not invent that reader or authentication channel.
- Root product commands: expose only typed no-path operations from the trusted main window. Root attaches to the verified environment after a restart using its existing authenticated identity proof, while lifecycle operations go to the owned system manager. Original `BootService.restart` and `withStopped` already leave other base directories alone. Native installation additionally must validate an existing unit's exact base directory/program/profile before any stop/repoint; do not silently replace another installation with the same per-user label.
- Exposure: call the existing `owner-control/ExposureRuntime.ts` original-service adapter. Apply desired settings and policy before constructing the next private child bootstrap; publish effective status only after authenticated host readiness. LAN and Tailscale Serve are distinct; retain original route ownership checks and scopes. The present adapter tests do not open a listener or configure a route.
- Direct-host migration: an already-running C21/direct host remains usable by its paired clients. Do not signal its persisted PID, delete its SQLite ownership lock, overwrite its runtime record, or launch a second writer. Migration requires an explicit shutdown under a still-captured owner, an independently authenticated in-process migration extension, or an operator-completed clean stop. An inherited original service IPC channel cannot be recovered from a runtime PID record. Existing data, environment identity and grants must be retained once the exclusive transition is possible.
- Updates: do not advertise `boot-service`/desktop-managed update capability until an owned artifact feed, profile4 installer/preflight, version migration, trial/rollback and exact signature/provenance policy exist. The original raw CLI/release helpers are not globally retargeted by these five records; do not expose them as configured Blackcrab distribution. Only the candidate native-local installation flow is prepared here.

## Verification

Run `node --test fork-integration/boot-service/boot-service.test.mjs` with the existing repository dependencies. **13 tests pass**, including exact source/diff/license provenance, actual original launchd/systemd renderers and manager plans, original codec semantics plus protocol4 refusal, real producer-verifier receipts, invalid pins/aliases/tampering, original typed Effect failures, staging-before-validation/commit ordering, updater denial before external effects, and actual original Launcher subprocess fixtures. Those subprocesses commit a prepared trial, roll back database bytes/start the previous version after failure, idle on exit78 without restoring over another owner, and stop only captured children while an unrelated owned fixture survives. No launchctl/systemctl command, service install, network call, cloud account, provider turn or production host is involved.

Strict pinned `effect-tsgo@0.67.1` TSRS no-emit validation passed for the five candidate modules, the typed adapter and their transitive original server graph using the pinned dependency cache. The probe uses the original strict optional/indexed-access flags and explicit unchanged cached declarations. This is a focused typecheck, not a complete monorepo lint/build or native boot-service acceptance.
